## 1. 提案時の背景と問題

- **現状**:
  - `Room` 検出は実装済みだが、成立した Room は半透明オーバーレイ表示のみで**ゲームプレイ上の意味を持たない**（[room_detection.md](../room_detection.md) §1 が「将来の Room 系ゲームプレイ機能の基盤」と明記）。
  - 電力（Soul Energy）は Yard 単位の PowerGrid が稼働中だが、消費側が Outdoor Lamp のみで需要が伸びない。[soul_energy.md](../soul_energy.md) §11 も「Room 接続」「追加消費設備」を将来拡張として挙げている。
  - 水は `GatherWaterToTank` / `DeliverWaterToMixer` のバケツ手動搬送のみで、恒久的なインフラ表現がない。
- **問題**: 建設シミュレーションとしての中盤〜後半の目標（「部屋を作る意味」「電力を増やす動機」「物流から解放される達成感」）が欠けている。
- **なぜ今か**: Room・電力・水搬送という 3 つの土台がすべて揃った今が、それらを結合する「インフラ層」を設計する適切なタイミングである。

## 2. 世界観設定 (Lore & Concept)

地獄の王が求める大規模本設施設（「罪人大楼（シナーズ・タワー）」等）の建設において、空調（気流）と衛生（給排水）は、人間界のような「労働者の快適さ」のためではなく、**「地獄の物理法則と王の建築基準」を満たすための必須インフラ**として存在する。

地獄の本設建築において、部屋とは壁で囲まれた空間ではない。王の基準では、瘴気を逃がす風路と、罪泥を流す水路が通って初めて、その空間は「使用に耐える苦役施設」として認可される。

```
┌──────────────────────────────────────────────┐
│                  【本設部屋】                │
│                                              │
│   [風のインフラ]                             │
│   叫びの風穴 💨 ────> 怠惰の瘴気(Miasma)を防止 │
│                                              │
│   [水のインフラ]                             │
│   骨の導水管 💧 ────> 罪泥(Lethe Sludge)を排泥 │
│                                              │
│   ※瘴気侵食または断水した本設設備は機能停止   │
└──────────────────────────────────────────────┘
```

### 2.1 王の建築基準：認可済み部屋（Sanctioned Room）

- **世界観**: `Room` 検出で成立した密閉空間は、地獄の行政上はまだ「密閉された罪の箱」に過ぎない。換気と排泥の条件を満たした部屋だけが **認可済み部屋（Sanctioned Room）** として扱われ、王庁の正式な認証を得る。
- **竣工検査の担い手**: 認可の判定はゲーム的には自動だが、世界観上は**下級官吏である使い魔**（→ [world_lore.md](../world_lore.md) §4.1）が王庁に竣工検査書を提出する体裁を取る。使い魔が監督官と検査官を兼ねるため、部屋が認可されるたびに使い魔が誇らしげにするなどの演出余地がある。
- **ゲーム的意味**　換気を満たし、排泥できる部屋を王庁が認可する。換気不足は所長に改善を促す。設備ごとの瘴気保護は将来の濃度計算を条件とする。
- **UI表現案**　認可、換気、排泥を独立して表示する。自然換気の三状態は「良好」「換気不足」「外気交換なし」。

### 2.2 風のインフラ：怠惰の侵食を防ぐ「風の循環」

- **世界観**: 密閉された部屋（Room）を放置すると、空間に囚われた魂たちの「怠惰の念」が「**怠惰の瘴気（Miasma）**」として物質化し、室内に滞留する。この瘴気は本設の石造建築を腐食させ、機械設備を「怠惰の呪い」で機能停止させる。王は瘴気に塗れた施設の稼働を認めないため、部屋には必ず風を循環させる設備が義務付けられる。
- **既存カノンとの接続**: 怠惰の瘴気は新規設定ではない。[world_lore.md](../world_lore.md) §2.2 で屋外に漂う「薄紫色の靄」がすでに怠惰の瘴気と定義されており、§1.2 では懶惰の野の特徴として「遅延と停滞が常態化」した時間の流れが設定されている。本提案はこれを**「屋外では薄く拡散している瘴気が、密閉空間では濃縮される」**という一貫した物理法則に昇格させるものである。集会スポットの紫オーラ（怠惰の象徴）と同系色で表現することで、「紫 = 怠惰の濃度」という色彩言語が世界全体で統一される。
- **停滞現象としての瘴気**　将来は室内で瘴気が蓄積すると歯車や炉の動作周期が鈍るなどの演出を検討する。症状は発生源、屋外背景、滞留時間と除去に応じる。

### 2.3 水のインフラ：罪泥の堆積を洗い流す「骨の導水路」

- **世界観**: 本設の建物や設備が稼働すると、魂たちの活動摩擦により、生前の罪が形となった黒いヘドロ「**罪泥（Lethe Sludge）**」が物理的に堆積する。これを放置すると、設備は目詰まりを起こして機能停止する。そのため、「忘却の川」から水を引いて罪泥を洗い流し、排泥するインフラ配管が必要となる。
- **忘却の川の水の性質**: 忘却の川の水は清潔な水ではなく、**設備にこびりついた罪の記憶を剥がす溶媒**である（[world_lore.md](../world_lore.md) §2.1: 生前の記憶を流す川 / §5.2: 黒く濁った液体）。断水した設備は汚れるのではなく、**過去の罪を思い出して自壊的に停止する**。
- **骨の配管の由来**: 導水管の素材である骨は「怠惰な魂の成れの果て」（[world_lore.md](../world_lore.md) §5.2）。つまりこのインフラは、**怠けて骨になった魂たちの中を、罪の記憶を溶かす黒い水が流れ続ける**という構造であり、罪人大楼プロジェクトの皮肉（怠惰の罪人に建設をさせる）と響き合う。
- **仮設の免除**: `MudMixer`（泥ミキサー）や `SoulSpa` などの仮設・現場設備は、王の建築基準（インフラ要件）の対象外とされ、罪泥の堆積を無視して手動の水搬送で稼働できる。応急設備に王の監査は入らない——これはゲーム的にも「序盤の遊びを壊さない」「詰み状態を作らない」安全弁を兼ねる（→ §9 リスク）。

## 3. 目的（Goals）

- 空調・衛生を人間界の概念から脱却させ、**「怠惰の瘴気（風）」と「罪泥の排泥（水）」という地獄の建築ルール**として導入する。
- `Room` を「囲われた空間」から「王の基準に認可された本設空間」へ段階的に発展させ、Room 検出システムに初のゲームプレイ上の意味を与える。
- 密閉室と外気のつながりを所長が確認し、設備の配置で換気を改善できるようにする。将来の瘴気の侵食は室内に蓄積した物質から判定する。
- 川から Room 内の `SludgePurifier` へ水を送る「骨の導水管」ネットワークを構築し、Purifier の到達性から Room 単位の排泥状態と断水時の設備停止を制御する。
- 電化換気設備・取水門を **Soul Energy の新規消費者**として追加し、電力システムの需要側を拡充する（[soul_energy.md](../soul_energy.md) §11 の将来拡張に対応）。

## 4. 非目的（Non-Goals）

- **Soul の快適度・健康の管理はしない**。瘴気や罪泥が Soul のストレス・疲労に影響する仕様は入れない（快適度メーターに見えると苦役テーマが弱まる。→ §8 代替案）。
- 初期は室単位の定常気流。熱・湿度・物質濃度の時間変化は後続段階の対象とする。給排水の初期実装は接続で判定する。
- **新規資源は追加しない**。すべての新設備は既存資源（木材・岩・骨・砂・StasisMud）で建設できる。
- **仮設設備への配管強制はしない**。既存の MudMixer / Tank / SoulSpa のワークフローは一切変更しない。
- **罪泥をアイテム・エンティティとして物理配置しない**（初期実装では状態フラグのみ。視覚化は将来検討）。

## 6. 詳細設計

### 6.1 インフラ責務の切り分け

| 系統 | 判定単位 | 主な失敗状態 | ゲーム上の圧力 |
|:---|:---|:---|:---|
| **風（換気）** | 開口を介してつながる屋外と部屋 | 外気交換不足 | 給排気の向きと室間の経路を設計する |
| **水（排泥）** | `Room` 単位（Room 内 Purifier の到達性を集約） | `Unwatered` / 断水・泥詰まり | 川岸から本設区画まで配管網を計画する |

換気と給排水には別々の経路があり、それぞれの計算結果を部屋の認可に使う。

### 6.2 部屋の換気基準と瘴気

成立室の必要量は床枚数×0.05。有効外気は屋外とつながる開口に生じる空気交換と、部屋をまたぐ負荷の移送から求める。M1では「外気交換なし」「換気不足」「良好」の三状態を表示する。将来、瘴気を扱う段階で発生・移送・排出を時間積分して濃度と滞留時間を求める。[室内空気と空調](../indoor_air.md)

認可は換気と排泥の両方を必要とする。断水時の停止は本設設備に適用し、既存の仮設設備で復旧作業を続けられる。

### 6.3 流体ネットワーク（排泥システム）

- `LetheIntakeGate`（供給源） → `OssuaryConduit`（配管） → `SludgePurifier`（消費者）を、電力グリッドと同様のグラフ接続（流体グリッド）で結ぶ。
- 接続判定は配管タイルの 4 近傍連結成分。流量計算はせず「稼働中の取水門に到達できるか」の bool のみ（Non-Goal 準拠）。
- 配管が取水門と繋がっていない、または取水門が停電している場合、その `SludgePurifier` 個体に `Unwatered` を付けて動作を停止する。
- Room 内に `Unwatered` でない Purifier が 1 基以上あれば `RoomDrainageState::Drained`、Purifier がないか全基が `Unwatered` なら `RoomDrainageState::Unwatered` とする。複数基のうち一部だけが断水した場合、到達不能な Purifier 個体だけを停止し、Room と他の本設設備は `Drained` を維持する。判定は network reachability → Purifier 個体状態 → Room drainage → sanction / disabled の一方向とし、`InfrastructureDisabled` を排泥判定の入力へ戻さない。
- `SludgeBasin` を導入する場合、供給不足や一時停電が起きても短時間だけ停止を猶予できる。バッファ満杯で関連設備は停止する（M4 評価後の follow-up）。

### 6.4 ECS 設計案（既存パターンの踏襲）

【決定済み】換気・流体のコンポーネント / Relationship / recalc システムは**新設クレート `crates/hw_infra`** に集約する（`hw_energy` は電力専任のまま変更しない。依存方向は `hw_infra` → `hw_energy`（`Unpowered` 参照）を想定）。`PowerConsumer` / `Unpowered` と Relationship の型パターンは `hw_energy` を参照するが、電力 lifecycle と cross-domain system ordering は現行どおり root `bevy_app` の adapter で接続し、leaf crate の実装をそのまま複製しない。

| 要素 | 電力（実装済み） | 換気（本提案） | 流体（本提案) |
|:---|:---|:---|:---|
| グリッド実体 | `PowerGrid`（Yard単位） | 屋外・室・開口のグラフ | `FluidGrid`（配管連結成分単位） |
| 供給側 Relationship | `GeneratesFor(grid)` | 建築と屋外境界から経路を再構築 | `SuppliesTo(grid)` |
| 消費側 Relationship | `ConsumesFrom(grid)` | —（部屋内判定） | `DrainsFrom(grid)` |
| 派生状態 | `PowerSupplyState` + 互換`Unpowered` | `RoomVentilation` | `RoomDrainageState` / Purifier の `Unwatered` |
| 本設設備への停止反映 | 消費設備自身を停止 | M5以降に濃度に応じて検討 | 断水時に本設設備の給水要件を評価 |
| 再計算システム | `grid_recalc_system` | `update_room_ventilation` | `fluid_grid_recalc_system` |
| 視覚反映 | `PoweredVisualState`（VisualMirror） | Room overlay 色変更 | 同 VisualMirror パターン |

※ **重要な実装上の注意（Room の揮発性）**: [room_detection.md](../room_detection.md) §4.3 の通り、Room エンティティは再検出のたびに**全 despawn → 再スポーン**される。したがって:
- Room を Target とする Relationship（`VentilatesFor` 等）は再検出のたびに消滅する。素直に永続 Relationship を張るのではなく、**床設備は `RoomTileLookup`、壁設備は計画で追加する `RoomBoundaryLookup` から Room を毎回逆引きする**（電力と違い供給側の永続登録が不要になり、despawn 問題を回避できる）。
- 自然換気の圧力と流量を建築状態から復元する。将来の瘴気・熱・湿気は各室に残る物質量・熱の蓄積量を保存する。

- **Scourge Fan の電力接続**: 既存の`PowerConsumer + PowerConsumerPolicy`とroot energy topology reconcilerを使う。
  PowerGrid entityはYard所有のまま、owner resolverをpaired Siteまで拡張する。pairを解決できない送風機は
  `Disconnected + Unpowered`のままとし、設置時UIで警告する。HVAC側でallocatorを複製しない。
- **配管の dirty 追跡**: 導水管の追加・削除では topology dirty、取水門の通電変化では supply dirty を立てる。連結成分の再構築は topology dirty frame に限定し、停電だけで flood fill を再実行しない。

### 6.5 進行段階（プレイヤー体験）

| 段階 | 解禁される考え方 | プレイヤー体験 | 依存する既存システム |
|:---|:---|:---|:---|
| 序盤 | 仮設設備と手動水搬送 | 屋外作業・仮設拠点で建設を始める | バケツ搬送（実装済み） |
| 中盤 | `Room` 成立と小規模換気 | 小部屋を作り、風穴・煙突で換気基準を満たす | Room 検出（実装済み） |
| 中盤後半 | 電力付き強制換気 | 大部屋の換気基準を維持し、発電 Soul の配分を悩む | Soul Energy（実装済み） |
| 後半 | 導水・排泥ネットワーク | 川岸から本設区画へ導水管を伸ばし、換気と排泥を満たして初めて Room の認可を取る | 本提案の流体グリッド |

電化換気は「Dream トレードオフ三角形」（[soul_energy.md](../soul_energy.md) §10）に直接接続する: 大部屋の換気基準を維持するには発電 Soul が要り、発電 Soul を増やせば労働力が減る。**部屋を広くする欲と電力予算の綱引き**が中盤のマクロ判断になり、後半の排泥網完成によって初めて Room 認可へ到達する。

## 8. 代替案と比較

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **人間界のエアコン・トイレの直訳導入** | 不採用 | 地獄で働く魂たちに「快適な冷気」や「衛生的なトイレ」を用意するのは世界観（地獄の苦役）と矛盾する。「建物を蝕む瘴気の換気」と「動作を阻害する罪泥の洗い流し」という建築基準の問題に翻訳する。 |
| **仮設設備（MudMixer や SoulSpa）も配管接続する** | 不採用 | これらは現場の応急設備。 本設フェーズになって初めて本格的な設備工事が要るという進行感・カタルシスを重視する。また仮設免除は「インフラ全停止でも復旧手段が残る」安全弁でもある。 |
| **部屋快適度メーターとして実装する** | 不採用 | Soul の快適性管理に見えると苦役テーマが弱くなる。あくまで「王の認可」「設備の稼働条件」「建築基準違反」として表現する。 |
| **換気用ダクトを敷く** | M2で検討 | 自然換気は建物の開口を使い、機械換気では離れた給排気端をダクトで結ぶ。 |
| **流体に流量・圧力の数値シミュレーションを入れる** | 不採用 | 接続 bool で十分ゲームになる。数値シミュレーションはパフォーマンスコストと理解コストに見合わない（Non-Goal）。 |

## 9. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Room再生成 | 時間発展する瘴気が初期化される | M1の換気は再計算、M5以降は重複容積で蓄積量を引き継ぐ |
| 停電時の換気不足 | 生産の停滞 | 自然換気、仮設設備、手動搬送を復旧経路として残す |
| 電力需要の急増で既存バランス崩壊 | Lamp 運用が割を食う | 送風機 0.5W / 取水門 1.0W を初期値として採用し、M2 / M3 の手動プレイで調整 |
| 配管連結成分の再計算コスト | 大規模配管網でスパイク | topology dirty / supply dirty を分離し、連結成分の再構築を topology dirty frame に限定する |
| Site 内の送風機が Yard grid を解決できず黙って動かない | プレイヤーが原因不明のまま放置 | paired Site から Yard grid を解決し、失敗時は設置ゴーストと info panel に `no grid` を表示 |
| セーブ互換 | 環境状態の消失 | M1は部屋・外壁・完成した風穴から再計算。M5以降は蓄積量と運転設定を保存し、流量は再計算する |
