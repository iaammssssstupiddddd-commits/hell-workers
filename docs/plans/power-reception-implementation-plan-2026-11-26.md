## 1. 最初に通す操作

**M1の完成条件は、通常のゲームで「管理 → 契約 → 川辺の夜普請」から受注し、木材を届けてA点の盤を据え、所長が準備完了を連絡し、外部から初めて電気が届いた時刻を契約書で読めること。** 全負荷が停止していても受電できる。M2で取水・夜間照明・泥づくりを接続し、指定床5マスと灯2基の引渡し、請求、盤の返却まで遊べるようにする。

案件ごとの受電条件は、入札要件と合意した工事計画を反映した請負契約に固定する。初回の例はA点、仮設受電盤1面、容量2.0 W、当該夜番の18:00までの受電、翌朝6:00までの引渡し。盤は王側から貸与し、台木2本は請負側が運ぶ。単位・数量・料金の調整は案件データで行う。新しい案件データを導入した後も、受注済み案件は保存した条項で判定する。

## 3. M1 ― 契約に沿って最初の受電を成立させる

### 変更1　契約と保存を先に通す

- 最初の1件をRustの案件定義として用意する。既存の初期工区からA点・灯2基・床工事の範囲を求め、通常の配置条件、猫車の通路、既設の取水門から浄化盤までの給水を確認する。候補を見つけた時点で契約図を提示する。受注時に同じ候補・条件・残高を照合し、失敗すれば理由を返す。受注の再送で二つ目の契約や貸与は生じない。
- 反射登録・保存対象・root回収の各リストへ追加し、既存の給水所検査と並べて新規案件を検査する。契約なしは未受注。重複案件、孤立した指名、異なるA点、未来の実受電、検収前の精算、負の計量値は候補ワールドの段階で拒否する。追加型だけで読める設計とし、旧v0/v1と給水所進行中の保存データで往復を確認する。[地図の基準点](../../crates/hw_world/src/anchor.rs)・[保存スキーマ](../../crates/bevy_app/src/systems/save/schema.rs)・[検証の入口](../../crates/bevy_app/src/systems/save/rehydrate/candidate/topology/mod.rs)
- **この変更の出口**　給水所と夜普請を同時に受注した世界を保存・再開でき、両案件の対象・期限・残高が一致する。夜普請が未受注なら貸与盤も外部電力も発生しない。

### 変更2　契約図から盤を建てる

- 管理の契約タブは案件を選んで一枚の契約書を表示する。「現地へ」は未施工のA点の座標にも移動できる。「指定盤を施工」は契約と指名を持った配置操作にし、プレビューと確定の双方で同じA点・占用・工区を検査する。受電盤は通常の自由配置一覧に出さず、固有の仮設建物として1×1・木材2で設計する。空調・水道専用の `Equipment` 一覧から独立させる。[配置入力](../../crates/bevy_app/src/interface/selection/building_place/mod.rs)・[建物の配置形状](../../crates/hw_jobs/src/placement_geometry.rs)
- 既存の `Blueprint`、`DeliverToBlueprint`、`Build` を順に使う。竣工で設計図から完成盤へ占用と指名を同じ確定処理で移す。施工中の取消は搬入済みの木材を既存経路で戻し、貸与1面を次の据付に使える状態へ戻す。完成盤はA点に固定し、移設操作では契約を移さない。撤去して同地点に据え直すときは別の指名で連絡を取り直す。[搬送要求](../../crates/hw_logistics/src/transport_request/producer/blueprint.rs)・[竣工時の所有移管](../../crates/bevy_app/src/systems/jobs/building_completion/mod.rs)・[施工取消](../../crates/bevy_app/src/systems/jobs/blueprint_cancellation.rs)
- 通常表示の最初の版には、1マスの盤本体・表示器・A点の印・予定線を用意する。盤の初期表示とロード時の再表示を同じ建物表示経路へ接続する。表示器は供給口の状態を読む。正式モデルはこの仮モデルと差し替え、通常距離・遠景で盤と荷受け灯を見分けられるか確かめる。[建物の表示経路](../../crates/bevy_app/src/systems/jobs/building_completion/spawn.rs)・[制作点数と受入条件](power-reception-and-use-plan-2026-11-26.md)
- **この変更の出口**　受注→配置→実搬送→竣工を通常操作で通せる。盤が完成した直後の表示は「準備完了の連絡待ち」。木材1本の時点、隣のマス、他の案件からの連絡要求では先に進まない。

### 変更3　準備完了の連絡と供給開始を接続する

供給側と現場側は独立して進む。契約上の締切、王側の作業予定、実際に起きた時刻を別フィールドにする。供給側の準備と所長からの連絡の双方がそろったとき、同じ判定関数で供給開始を試みる。

| 入力 | 成立条件と確定する結果 |
| --- | --- |
| 所長が「準備完了を連絡」 | 現在のワールド、選択した盤、案件・指名、A点・仕様・完成・有効な所属を再照合し、連絡済みの指名を記録する。王側が準備中なら「外部供給待ち」。 |
| 王側の引込準備が完了 | ゲーム時計に従って供給側を準備済みにする。所長の連絡がまだなら待機。供給開始を確定する際に、指定盤が現在も一致し受電可能であることを再検査する。 |
| 指定盤への外部供給が開始 | 供給口を通電中にし、初回ならその実ゲーム時刻を契約に記録して通知を一度出す。負荷0 Wで成立する。期限内の判定は実時刻が締切以下。灯の点灯試験はM2の別操作。 |
| 盤の撤去・供給停止・再開 | 撤去は現在の給電と旧指名への連絡を無効にする。過去の初回受電は残す。同じ案件で再施工したときも初回実績を上書きしない。供給終了後は検収済みの案件から再通電しない。 |

受注・連絡・試験・精算は型付きの `UiIntent` を通す。閲覧と地図移動はポーズ中も可能。変更操作はポーズ中、入力を覆う画面の表示中、復旧失敗中に破棄する。契約書の操作は表示中の案件を、盤詳細からの連絡は表示中の盤を照合する。要求の重複やロード前に作った要求で契約を進めない。[入力の定義](../../crates/hw_ui/src/intents.rs)・[操作の処理](../../crates/bevy_app/src/interface/ui/interaction/intent_handler.rs)・[シミュレーション側の確定処理](../../crates/bevy_app/src/systems/ui_domain_commit.rs)

**M1の受入**　通常ワールドでは既設の取水をSpaに任せ、指定盤には負荷をつながず、現場先行と王側先行の両方を試す。停止・保存後、停止したままロードして「受電済み・使用0 W」と元の日時を確認する。別途、空調・水道設備が一つもなく契約と盤だけがある最小の保存テストを作る。`wake_domains_after_load` がこの場合にも表示と電力状態を再構築でき、通知・徴収・試験を繰り返さないことを検証する。[ロード後の再構築](../../crates/bevy_app/src/systems/save/rehydrate.rs)

**時刻と実行順。** 盤の竣工・取消・解体を反映した後、既存の `register_soul_energy_pipeline` で供給口、運転要求、回路の変更・削除を検出する。所属の再構成→Spaの実出力→配電→結果反映の順序を使う。荷下ろしの照合では荷を降ろした時点に有効だった配電結果を記録し、その後の点灯で帳消しにしない。給水品質は対象盤の `PostActor` の水道更新後に読む。試し点灯は押下後の配電確定を待つ。検収判定と保存が重なる場合は、確定前か確定後の整合した一方だけを保存する。[本番の実行順](../../crates/bevy_app/src/plugins/logic.rs)・[ゲーム時計](../../crates/bevy_app/src/systems/time.rs)

**請求と終了。** 使用量は前回の外部実給電W×経過ゲーム秒÷3600を料金台帳に積む。負荷・供給元・通電状態が変わる直前と、保存・検収時に直前区間を締める。一定負荷のまま保存しても端数を失わず、停止中の再読込や同時刻の再計算は0 Wh。試作の費用負担案は、受注時に契約記載の引込・固定・撤去の定額分を一度支払い、検収時に従量分と報酬を確定する。受領操作では共有Dreamと未精算→精算済みを同時に更新する。差引の支払いに残高が不足すれば金額を表示し、検収実績と明細を保持したまま精算を再試行できる。外部供給・従量課金は検収で終了し、解体完了で貸与品を返却済みにする。

## 5. 実装担当への引継ぎ・検証

1. **最初の差分は変更1。** 上記基点から既存の給水所の受注・保存試験と、指定点での配置可否を確認し、案件固有の型・受注処理・保存往復テストを一組で追加する。以降は変更2、3をそれぞれ通常操作につないでM1を検収する。色や盤の最終モデルを先に決める必要はない。
2. **境界値を自動テストにする。** 期限の例では実受電18:00は期限内、18:01は遅延。未連絡、別盤、撤去済み、空の電力網、現場発電単独は実績なし。連絡と供給側完了が同時でも実績は一度。1倍・4倍・停止・途中再開で同じ時刻の操作列を与え、実受電日時・使用量・引渡結果を比較する。案件なしの旧セーブ、給水所との共存、不正な候補ロードからの復旧を含める。
3. **正規経路で試遊する。** M1は受注から実搬送・竣工・連絡・実受電、M2は16時の準備済みセーブと通常生成ワールドの双方から夜荷・試し点灯・精算まで確認する。受電済み0 W、王側先行、外部待ち、ミキサー待機、精算後の5場面で地図・契約書・盤の表示と世界状態を照合する。給水所の既存受入シナリオも保持する。[既存契約の実画面シナリオ](../../scripts/ui_first_waterworks.py)・[現場別の試遊条件](power-reception-and-use-plan-2026-11-26.md)
4. **段階ごとに検証する。** 実装は着手時の基点を固定して目的別ブランチで進める。Rust変更は `python3 scripts/dev.py check`、対象クレートのテスト、警告0件のworkspace Clippyを通す。受電条件・画面操作・理由表示はHelpと仕様書に反映し、本番入力の試遊にはリポジトリのnative受入手順を使う。完了時は同一対象の変更別CIまたはローカル同等検査、primaryのstorage checkを通す。[開発手順](../DEVELOPMENT.md)・[Help](../help-screen.md)・[保存仕様](../save_load.md)・[検証データ管理](../development-infra/validation-storage-workflow.md)

**戻す単位。** M2の配電切替は案件回路を持つ設備に限定する。問題が出たら既設自家発電・手練りの既存経路を使えるよう保ち、M1の初回受電履歴は維持する。開発中に新規案件を提示停止する場合も、発行済み案件の保存型・読み込み・精算経路は保持する。M3は初回案件の合格後、新しい本設契約と設備試験を同じ仕組みに接続する。

### M1の実機確認（2026-11-26）

既設の取水・導水・屋内浄化盤と現場電源のある工区から、契約・設計図・受電記録を持たずに開始。通常の契約画面で受注し、A点（72, 41）に施工を指示した。別々の木材2個が同じ設計図に搬入され、完成した指名1の盤で準備完了を連絡。王側の引込準備を待ち、契約書に「初回受電 1日目 17:30（期限内）」「外部受電中　使用 0 W」が表示された。停止中の保存・読込後も実時刻・残高・指名が一致した。6場面・OS入力58件を検証済み。給電側が先に準備済みの場合、期限ちょうどと遅延、再施工は自動試験で確認した。
